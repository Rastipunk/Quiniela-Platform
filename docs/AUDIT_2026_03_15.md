## 1. ARQUITECTURA

### ARQ-01: Singleton Prisma sin manejo de desconexión
- **Estado:** `[x]` Corregido
- **Archivos:** `backend/src/db.ts`, `backend/src/server.ts`
- **Problema:** No había `$disconnect()` en shutdown. En Railway redeploy, conexiones DB quedaban como zombies.
- **Fix:** Graceful shutdown con `SIGTERM`/`SIGINT` → stop HTTP, stop cron jobs, `prisma.$disconnect()`, force exit a 10s.
- **Commit:** `d03d3be`

### ARQ-02: Lógica de negocio mezclada en route handlers
- **Estado:** `[x]` Corregido — 10/10 route files migrados
- **Archivos:** 10 servicios creados en `backend/src/services/`
- **Problema:** Los route handlers mezclan validación, lógica de negocio, acceso a DB, envío de emails y auditoría. Imposible reutilizar y testear.
- **Patrón aplicado:** `ServiceError` class con `code` + `statusHint` + `extra`. Servicios lanzan `ServiceError`, routes los mapean a HTTP con `handleServiceError()`. `AuditContext` para pasar ip/userAgent sin dependencia de Express. `fireAndForget()` para side effects no-críticos.
- **Progreso:**
  - `[x]` **auth** — `services/authService.ts` (639 líneas). Routes: 1037 → 248 líneas (76% reducción).
  - `[x]` **corporate** — `services/corporateService.ts`. Routes: 513 → ~160 líneas.
  - `[x]` **results** — `services/resultService.ts`. Routes: 634 → ~80 líneas.
  - `[x]` **poolAdmin** — `services/poolAdminService.ts`. Routes: 1520 → ~250 líneas.
  - `[x]` **poolMembers** — `services/poolMemberService.ts`. Routes: 523 → ~195 líneas.
  - `[x]` **poolOverview** — `services/poolOverviewService.ts`. Routes: 574 → ~55 líneas.
  - `[x]` **admin** — `services/adminService.ts`. Routes: 1332 → ~113 líneas.
  - `[x]` **adminInstances** — `services/adminInstanceService.ts`. Routes: 942 → ~300 líneas.
  - `[x]` **picks** — `services/pickService.ts`. Routes: 281 → ~90 líneas.
  - `[x]` **groupStandings** — `services/groupStandingsService.ts`. Routes: 555 → ~170 líneas.

  **Archivos pequeños (< 250 líneas) — No requieren extracción:**
  - `pools.ts` (237) — Solo CRUD básico, ya delegado.
  - `poolInvites.ts` (302) — Invite code management, simple.
  - `me.ts` (191) — Profile + preferences, simple.

  - `adminTemplates.ts` (235), `adminSettings.ts` (442), `adminCorporate.ts` (411) — Admin CRUD, bajo tráfico.

### ARQ-03: Múltiples routers montados en el mismo path
- **Estado:** `[x]` Corregido
- **Archivos:** `backend/src/server.ts`, `backend/src/routes/pools.ts`, `backend/src/routes/admin.ts`
- **Problema:** 6 routers montados en `/pools`, 5 en `/admin`. Funciona en Express pero un conflicto de rutas entre routers es silencioso y difícil de debuggear.
- **Fix:** Router padre compone sub-routers con `router.use()`. `pools.ts` monta 9 sub-routers (picks, results, structural*, groupStandings, members, invites, admin, overview). `admin.ts` monta 4 sub-routers (templates, instances, settings, corporate). `server.ts` pasa de 12 líneas de montaje a 3.

### ARQ-04: Sin capa de DTOs / Serializers
- **Estado:** `[~]` Mitigado — riesgo aceptado tras auditoría
- **Archivos:** `backend/src/lib/serializers.ts` (centralizado), todos los servicios
- **Problema original:** Las queries Prisma se envían casi directamente al cliente. Si se agrega un campo sensible al modelo, se filtra al frontend automáticamente.
- **Resultado de auditoría (2026-03-15):** Se revisaron 13 archivos de servicios + 4 rutas. **No se encontraron fugas de datos sensibles.** Todas las queries de User usan `select` explícito. `serializeUser()` centralizado en `lib/serializers.ts`. Otras entidades (Pool, Pick, Result) no tienen campos sensibles inherentes.
- **Acción:** `serializeUser()` movido de authService a `lib/serializers.ts` para reutilización. No se justifica crear serializers formales para entidades sin campos sensibles.

### ARQ-05: Frontend api.ts monolítico (~1340 líneas)
- **Estado:** `[x]` Corregido
- **Archivos:** `frontend-next/src/lib/api/` (9 módulos + barrel index)
- **Problema:** Todas las llamadas API en un solo archivo. Difícil de navegar, mantener y hacer code splitting.
- **Fix:** Modularizado por dominio: `client.ts` (fetch wrapper), `auth.ts`, `user.ts`, `pools.ts`, `picks.ts`, `groupStandings.ts`, `scoring.ts`, `corporate.ts`, `admin.ts`. Barrel re-export en `index.ts` mantiene imports existentes (`@/lib/api`) sin cambios en 40+ consumidores. Original `api.ts` eliminado.

### ARQ-06: Cobertura de tests insuficiente
- **Estado:** `[x]` Corregido — hallazgo original era parcialmente incorrecto
- **Archivos:** 9 archivos `*.test.ts` (5 existentes + 4 nuevos)
- **Problema original:** Se reportó "sin tests automatizados", pero ya existían 5 archivos con 156 tests (scoring, presets, breakdowns, email, deadline reminders).
- **Fix:** Agregados 4 archivos para áreas faltantes: `poolStateMachine.test.ts` (26 tests — transiciones + validaciones), `serializers.test.ts` (3 tests — stripping de campos sensibles), `jwt.test.ts` (7 tests — sign/verify/tampering), `password.test.ts` (4 tests — hash/verify). Total: **9 archivos, 196 tests, todos pasan.**

## 2. BUENAS PRÁCTICAS DE PROGRAMACIÓN

### BP-01: Emails fire-and-forget sin manejo de fallos
- **Estado:** `[ ]`
- **Archivos:** `backend/src/lib/email.ts`, múltiples routes
- **Problema:** Emails se envían sin `await` y sin `catch`. Si Resend falla, nadie se entera. Un usuario podría no recibir verificación sin rastro del error.
- **Fix propuesto:** Al menos: wrappear en try/catch con logging. Ideal: cola de reintentos (BullMQ o similar).

### BP-02: Route handlers async sin wrapper de errores
- **Estado:** `[ ]`
- **Archivos:** Todos los routes
- **Problema:** Express 4/5 no captura automáticamente errores de Promises rechazadas en todos los casos. Un handler async que lance excepción puede no llegar al error handler global.
- **Fix propuesto:** Crear `asyncHandler` wrapper: `const asyncHandler = (fn) => (req, res, next) => Promise.resolve(fn(req, res, next)).catch(next);`

### BP-03: JWT expira a 4h pero cookie dura 7 días
- **Estado:** `[ ]`
- **Archivos:** `backend/src/lib/jwt.ts:15`, `backend/src/lib/authCookies.ts:5`
- **Problema:** El navegador envía cookie con JWT expirado durante ~6.8 días. No hay refresh token — el usuario recibe 401 silencioso y debe re-loguearse.
- **Fix propuesto:** Opción A: Alinear cookie maxAge con JWT expiry (4h). Opción B: Implementar refresh tokens.

### BP-04: Inline styles masivos en componentes React
- **Estado:** `[ ]` (parcialmente mitigado con theme.ts en MD-01)
- **Archivos:** Mayoría de componentes frontend
- **Problema:** `style={{...}}` extensivos impiden pseudo-clases (:hover, :focus), no se cachean, y hacen los componentes difíciles de leer.
- **Nota:** theme.ts ya centraliza tokens. La migración a CSS modules sería un cambio grande — evaluar si vale la pena vs adopción progresiva.

### BP-05: Comentarios triviales en español en código
- **Estado:** `[ ]`
- **Archivos:** `backend/src/db.ts` (ya corregido), otros archivos dispersos
- **Problema:** Comentarios como `// Comentario en español: una sola instancia de Prisma` no aportan valor. El código debería ser auto-explicativo y los comentarios necesarios en inglés.
- **Fix propuesto:** Eliminar comentarios triviales, mantener solo los que explican "por qué" (no "qué").

## 3. SEGURIDAD INFORMÁTICA

### SEC-01: CORS permite requests sin Origin header
- **Estado:** `[ ]`
- **Archivos:** `backend/src/server.ts:51`
- **Problema:** `!origin` acepta cualquier request sin Origin (curl, scripts, server-to-server). CORS solo protege en navegadores. Combinado con SameSite=Lax es aceptable para REST API, pero es un riesgo a documentar.
- **Decisión pendiente:** ¿Aceptar como riesgo conocido o restringir?

### SEC-02: Rate limiting en memoria (no persistente)
- **Estado:** `[ ]`
- **Archivos:** `backend/src/middleware/rateLimit.ts`
- **Problema:** `express-rate-limit` usa `MemoryStore`. Si Railway escala a múltiples instancias o hace redeploy, contadores se reinician. Atacante puede esperar redeploy para resetear límites.
- **Fix propuesto:** Usar `rate-limit-postgresql` (ya tienes Postgres) o `rate-limit-redis`.

### SEC-03: Sin validación MIME type en uploads base64
- **Estado:** `[ ]`
- **Archivos:** `backend/src/routes/corporate.ts`, `backend/src/routes/feedback.ts`
- **Problema:** Logos y screenshots aceptan base64 hasta 700KB sin validar que sea imagen. Podría ser HTML, ejecutable, etc.
- **Fix propuesto:** Validar magic bytes (PNG: `iVBOR`, JPEG: `/9j/`, GIF: `R0lGOD`, WebP: `UklGR`).

### SEC-04: Password sin requisitos de complejidad
- **Estado:** `[ ]`
- **Archivos:** `backend/src/routes/auth.ts` (registro schema)
- **Problema:** Solo requiere 8 caracteres mínimo. Contraseñas como `12345678` son aceptadas.
- **Fix propuesto:** Agregar guía frontend de fortaleza. Considerar zxcvbn o reglas básicas (mayúscula + número).

### SEC-05: Sin revocación ni rotation de tokens
- **Estado:** `[ ]`
- **Archivos:** `backend/src/lib/jwt.ts`
- **Problema:** No hay blacklist de JWT. Token robado es válido 4 horas completas sin poder revocarlo.
- **Nota:** Para el volumen actual (~40 usuarios) el riesgo es bajo. Documentar como mejora futura.

### SEC-06: `unsafe-inline` en CSP para scripts
- **Estado:** `[ ]`
- **Archivos:** `frontend-next/next.config.ts:9`
- **Problema:** `'unsafe-inline'` debilita CSP contra XSS. Necesario actualmente para GA4 y Google Identity Services.
- **Fix propuesto:** Migrar a nonces con Next.js cuando el soporte sea estable. Por ahora documentar como riesgo aceptado.

### SEC-07: Logging puede exponer datos sensibles
- **Estado:** `[~]` Parcialmente mitigado en LO-03 del code review anterior
- **Archivos:** `backend/src/server.ts:117`
- **Problema:** `err.stack` podría contener datos de usuario si el error viene de una query con parámetros.
- **Nota:** LO-03 ya sanitizó `console.error` en 8 archivos. El error handler global aún logea stack completo.

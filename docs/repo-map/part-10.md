### backend/src/services/paymentService.test.ts

**Purpose:** Vitest unit suite for the payment service, exercising the Polar + Mercado Pago webhook handlers, checkout initiation (both gateways), the synchronous MP Brick path, IPN dedup semantics, and status queries — all against fully mocked Prisma and gateway clients. The tests double as living documentation of the payment regression fixes (F-4, F-5, #9, retryable-not-found, status-aware idempotency).

**What it does:**
- **Module mocks (top of file):** Stubs `../db` (Prisma) with hand-rolled `vi.fn()` jest-style mocks for `paymentEvent` (`findFirst`/`create`), `poolPayment` (`findUnique`/`findFirst`/`create`/`update`), `pool` (`findUnique`/`update`), `poolMember.findFirst`, `user.findUnique`, and `$transaction`. Also mocks `../lib/audit` (`writeAuditEvent`), `../lib/email` (`sendAdminNotification`, `sendPaymentReceiptEmail`), `../lib/asyncHelpers` (`fireAndForget`), `./polar/client` (`createCheckout`, `getCheckoutSession`), and `./mercadopago/client` (`processPaymentDirect`, `getPayment`, `getMpPublicKey` returning a fake key, `createPreference`). A comment notes `findFirst` replaced `findUnique` after the 20260519 migration made `polarEventId` nullable with a partial unique index (ADR-060).
- **Helpers:** `orderPaidPayload(overrides)` builds a canonical Polar `order.paid` webhook body with default pool/user/capacity metadata; `MOCK_PAYMENT` is the canonical PENDING PoolPayment fixture.
- **`beforeEach`:** clears all mocks and wires `$transaction` to a pass-through that invokes the callback with the `prisma` mock so inner `tx.*` calls hit the same mocks.
- **`describe("handleOrderPaid")`:** asserts capacity expansion on a fresh valid event (`pool.update` sets `maxParticipants: 50` and re-arms `poolFullNotifiedAt`/`capacityWarningNotifiedAt` to null); idempotent skip on duplicate `paymentEvent`; P2002 race rollback inside the tx (no payment/pool update); atomic commit of `paymentEvent.create` + `poolPayment.update` + `pool.update` in a single `$transaction` with `metaEventId` persisted in the same update (regression for the bug where the create lived outside the tx); skip when already COMPLETED; graceful return on missing `poolId`; graceful return on missing `checkout_id`; and `PAYMENT_NOT_FOUND_RETRYABLE` throw when no PoolPayment matches the checkout (no paymentEvent slot claimed before the throw, so retries can dedupe correctly).
- **`describe("handleOrderRefunded — retryable not-found")`:** asserts the refund handler also throws `PAYMENT_NOT_FOUND_RETRYABLE` when no PoolPayment matches the refund checkoutId.
- **`describe("handleCheckoutUpdated")`:** asserts terminal Polar statuses map to the new enum values — `expired`→`EXPIRED`, `canceled`→`CANCELLED` — each writing a `POLAR_WEBHOOK`/`checkout.updated` audit row; non-terminal `confirmed` writes only an audit row with no status transition; duplicate deliveries skip via the pre-check.
- **`describe("initiateCheckout")`:** FORBIDDEN when caller is not HOST; VALIDATION_ERROR when `targetCapacity <= current`; reuse of an existing PENDING checkout URL via `getCheckoutSession` (no new `createCheckout`); F-5 fix — the idempotency `findFirst` WHERE clause must include `userId` (so a CO_ADMIN doesn't get the HOST's checkout); F-4 fix — an `INITIATED` row is INSERTed with `polarCheckoutId: null` before the Polar call, then UPDATEd to `PENDING` with the real checkoutId plus a `SERVER`/`STATUS_TRANSITION` audit event; F-4 failure path — Polar throwing flips the row to `FAILED` and writes a `STATUS_TRANSITION` event with `reason: "polar_create_failed"`.
- **`describe("processMpPayment")`:** approved MP payment expands capacity (status COMPLETED + pool re-arm); rejected payment flips to FAILED without touching the pool. Notes the lookup is by `findUnique` on `PoolPayment.id` (real unique constraint).
- **`describe("initiateMpCheckout (idempotency)")`:** reuses an existing PENDING MP payment + preference (no new `createPreference`, no new row); creates an INITIATED row with `mpPreferenceId: null` then transitions to PENDING with the real preferenceId + a `SERVER`/`STATUS_TRANSITION` event; treats a legacy PENDING row with `mpPreferenceId: null` as non-reusable and creates a fresh INITIATED row.
- **`describe("handleMpWebhook")`:** expands capacity on an approved IPN; P2002 race rollback in the approved-branch tx; eventId includes the MP status (`mp-{id}-{status}`) so distinct statuses are distinct idempotency slots; a two-step walkthrough proving an intermediate `pending` webhook does NOT dedup-block a later `approved` webhook for the same payment; and `PAYMENT_NOT_FOUND_RETRYABLE` throw when the `external_reference` has no PoolPayment (no paymentEvent slot claimed first).
- **`describe("getPaymentStatus")`:** returns null when no payment exists for an active member; throws FORBIDDEN when the caller is not an active pool member.

**Exports:** none (test module).

**Key dependencies:** `vitest`, mocked `../db`, `../lib/audit`, `../lib/email`, `../lib/asyncHelpers`, `./polar/client`, `./mercadopago/client`; imports the real `ServiceError` from `./authService` and the system-under-test functions from `./paymentService`.

### backend/src/services/paymentService.ts

**Purpose:** The single source of truth for all pool-capacity payment business logic across both gateways (Polar/USD international and Mercado Pago/COP Colombia): checkout initiation, webhook processing, the synchronous MP Brick path, account-receivable (cuenta de cobro) redemption, idempotent completion, refunds, status queries, and the dual stale-payment reconcilers. ~2607 lines.

**What it does:**
- **Header invariants (docstring):** `Pool.maxParticipants` only mutates inside completion; price always computed server-side; webhooks idempotent via `PaymentEvent.polarEventId`; checkouts idempotent by reusing the PENDING checkout for the same pool.
- **CC redemption guard (`CcSnapshot` interface, `validateAccountReceivableForCheckout`):** Read-only pre-INSERT validator for cuenta-de-cobro redemptions. Loads the `accountReceivable`, throws `ServiceError` (NOT_FOUND/CONFLICT) if not PENDING, expired, capacity mismatch, currency mismatch, or — the pricing-drift safeguard (§11.7) — if the snapshot `amountCop`/`amountUsdCents` no longer matches live `pricing.ts` output. On drift it fires an admin notification (`cc_pricing_drift`) and blocks. Returns the snapshot.
- **`WebhookContext` interface:** Optional `webhookId` + `webhookTimestamp` threaded from the Polar route boundary into every PaymentEvent row (F-19).
- **`mpPurchaseValue(payment)`:** Resolves the COP value to report on analytics events — prefers the persisted `amountCop` column, else recomputes via `calculateUpgradePriceCop`. Explicitly never uses `amountUsd` (USD cents) for COP to avoid ~40x revenue underreporting.
- **Types:** `InitiateCheckoutInput` (userId/poolId/targetCapacity/locale + optional Meta advanced-matching signals fbp/fbc/IP/UA + optional `accountReceivableId` for CC redemption), `InitiateCheckoutResult`, `PaymentStatusResult` (note `amountUsd` is in MAJOR units with `currency` disambiguating; carries `transactionId` + `metaEventId` for Pixel/CAPI/GA4 dedup).
- **`initiateCheckout` (Polar):** Loads the pool with HOST/CORPORATE_HOST membership + organization; validates target > current capacity; computes price server-side via `calculateUpgradePrice`/`usdToCents`; F-5 idempotency `findFirst` scoped by `poolId+userId+status=PENDING+toCapacity`, re-fetching the live Polar session to reuse the URL (falls through to a new attempt on Polar error); validates CC snapshot if redeeming; F-4 INSERTs the PoolPayment as `INITIATED` BEFORE the Polar call (inside a tx that atomically flips the CC PENDING→REDEEMED via `updateMany` count guard when redeeming); builds locale-aware success/cancel URLs carrying `paymentId`; calls `polarCreateCheckout`; on failure transitions to `FAILED` + `SERVER`/`STATUS_TRANSITION` audit event and re-throws (5xx); on success transitions to `PENDING` with the checkoutId + audit event atomically; fire-and-forget `PAYMENT_CHECKOUT_CREATED` audit.
- **`MarkPaymentCompletedInput` + `markPaymentCompleted`:** THE single completion path for all four callers (Polar webhook, MP sync, MP IPN, MP reconciler). Triple idempotency (cheap `paymentEvent.findFirst` pre-check, `status === COMPLETED` entry guard, `polarEventId` UNIQUE inside the tx). Derives `isMp` from `source`/`mpPreferenceId`; reuses or mints a `metaEventId`. Atomic tx writes: `PaymentEvent`, `PoolPayment` (COMPLETED + polarOrderId + paidAtUtc + metaEventId + optional mpPaymentId), `Pool` (maxParticipants bump + re-arm notification flags), `AccountReceivable`→PAID (if linked CC), and an `AuditEvent` `PAYMENT_COMPLETED` row inside the tx. P2002 → silent no-op; other errors propagate. Post-tx fire-and-forget fan-out: admin notification (formatted with buyer/pool/amount/gateway), Meta CAPI `Purchase` (with advanced matching from persisted columns + user PII), GA4 `purchase`, and receipt email (with CC `consecutive` lookup, currency-correct amount formatting, locale via `resolveUserLocale`). Currency/affiliation/transactionId all derived from gateway, not hardcoded.
- **`handleOrderPaid` (Polar `order.paid`):** Thin parser — validates metadata (`poolId`+`toCapacity`) and `checkout_id`, resolves the PoolPayment by `polarCheckoutId` (`findFirst`), throws `PAYMENT_NOT_FOUND_RETRYABLE` on the checkout-vs-webhook race (so Polar retries / lands in DLQ), then delegates to `markPaymentCompleted`.
- **`handleOrderRefunded` (Polar `order.refunded`):** Idempotency pre-check; resolves payment by checkoutId; throws `PAYMENT_NOT_FOUND_RETRYABLE` on race; skips if already REFUNDED; atomic tx writes PaymentEvent + flips status to `REFUNDED` (NOTE: does NOT shrink `maxParticipants` to avoid evicting joined members); P2002 → skip. Fire-and-forget `PAYMENT_REFUNDED` audit, GA4 `refund` (same transaction_id to collapse onto the original), and a compensating Meta CAPI `Refund` custom event.
- **`handleCheckoutUpdated` (Polar `checkout.updated`):** Post-F-3 — persists EVERY delivery as a PaymentEvent audit row (uses `payload.data.id` as both checkout id and event id). Maps terminal statuses (`expired`→EXPIRED, `canceled`/`cancelled`→CANCELLED, `failed`→FAILED) onto the enum only when the row is PENDING/INITIATED; `succeeded`/`open`/`processing`/`confirmed` are audit-only. Atomic tx; P2002 skip; emits a GA4 `payment_failed` funnel event on terminal transitions.
- **`recordUnhandledPolarEvent`:** Persists any Polar event type lacking a dedicated handler (e.g. `customer.created`) as a PaymentEvent for the audit trail, linking to a PoolPayment when a checkout id is recoverable; handles missing event id (NULL polarEventId allowed by the partial index) and P2002 skip.
- **`RecordClientEventInput` + `recordClientEvent`:** Persists browser-emitted payment-attempt events (REDIRECT_INITIATED/REDIRECT_FAILED/USER_CANCELLED/CLIENT_ERROR) with `source=CLIENT` and NULL polarEventId. Validates the event type against `CLIENT_EVENT_TYPES` and enforces that `userId` owns the `poolPaymentId` (FORBIDDEN otherwise, without leaking existence).
- **`getPaymentStatus(userId, poolId)`:** Verifies ACTIVE membership (FORBIDDEN otherwise), returns the latest payment with amount converted to MAJOR units (USD cents/100 for USD; `mpPurchaseValue` for COP to fix the mislabeled-column bug), plus transactionId/metaEventId/paidAtUtc.
- **Polar reconciler (F-14):** `RECONCILE_ABANDONED_THRESHOLD_HOURS` (default 24) + `RECONCILE_GRACE_PERIOD_MINUTES` (default 15) env-tunable. `reconcileStalePayment(paymentId)` returns `ReconcileResult` and walks: NOOP for terminal rows; ABANDONED if no `polarCheckoutId` past threshold; queries `getCheckoutSession`; 404→ABANDONED; `succeeded`/`confirmed`→RESCUED (writes audit + admin notification but deliberately does NOT auto-complete — human reviews); `expired`→EXPIRED (releases linked CC via `releaseAccountReceivable`); `failed`→FAILED (releases CC; note this branch writes `RECONCILER_EVENT_TYPE.EXPIRED` as the eventType — see Flags); `open` past threshold→ABANDONED, else NOOP. Helpers `markAbandoned` (atomic ABANDONED + CC release + audit) and `writeReconcilerEvent`. `findStalePayments(batchSize)` selects Polar-only rows (`mpPreferenceId IS NULL`, INITIATED/PENDING, older than grace), oldest-first.
- **MP reconciler:** `MP_RECONCILE_ABANDONED_THRESHOLD_HOURS`/`MP_RECONCILE_GRACE_PERIOD_MINUTES` env-tunable. `reconcileStaleMpPayment(paymentId)` returns `MpReconcileResult`: resolves MP payment id (uses `mpPaymentId`, else `searchPaymentByExternalReference` on the stored reference, persisting it back, else ABANDONED/NOOP); calls `getPayment`; `approved`→auto-completes via `markPaymentCompleted` (source RECONCILER); `rejected`/`cancelled`→FAILED + CC release; still in-flight past threshold→ABANDONED, else NOOP. `findStaleMpPayments(batchSize)` selects MP-only rows (`mpPreferenceId IS NOT NULL`), covered by the `PoolPayment_status_createdAtUtc_idx` index.
- **Mercado Pago checkout (`MpCheckoutData`, `initiateMpCheckout`):** Mirror of Polar init for the Payment Brick. Validates ownership + target capacity; computes `amountCop` via `calculateUpgradePriceCop` and `amountUsd`; F-5 idempotency scoped by userId+poolId+PENDING+toCapacity+currency=cop, reusing the existing preference when both `mpPreferenceId` and `polarCheckoutId` are present; mints a stable `reference` (`P4A-{poolId8}-{ts}`) stored in the `polarCheckoutId` column (dual-purpose, F-8 rename pending); validates CC snapshot for COP; F-4 INSERTs INITIATED (with `amountCop`, `currency: cop`, `mpPreferenceId: null`) BEFORE calling MP (CC-atomic tx when redeeming); calls `mpCreatePreference` with locale-aware back URLs + notification URL; on failure → FAILED + `mp_preference_create_failed` audit + re-throw; on success → PENDING + preferenceId + audit; fire-and-forget `MP_CHECKOUT_CREATED` audit. Returns Brick config (publicKey, paymentId, amountCop, reference, poolId, preferenceId).
- **`MpProcessInput` + `processMpPayment`:** Synchronous Brick path. Loads payment (NOT_FOUND / ALREADY_COMPLETED guards); enriches `formData` server-side with `external_reference`, description, and `additional_info.items` (unit_price in COP via `mpPurchaseValue`, explicitly not USD cents); calls `mpProcessPaymentDirect`; `approved`→`markPaymentCompleted` (source MP_SYNC, idempotency key `mp-{id}-approved` matching the IPN) then re-reads `metaEventId` for the Brick response; `rejected`→FAILED + GA4 `payment_failed`; `pending`/`in_process` deferred to the IPN. Notes `metaCookies`/IP/UA/country params are accepted for route compatibility but unused (read from persisted columns instead).
- **`handleMpWebhook(paymentMpId)` (MP IPN):** Verifies via `mpGetPayment`; builds status-aware idempotency key `mp-{id}-{status}` (so pending→approved transitions each get their own slot); pre-check skip; resolves payment by `polarCheckoutId`=reference, throwing `PAYMENT_NOT_FOUND_RETRYABLE` on race; detects refund signals; skips approved if already COMPLETED; defensively persists `mpPaymentId` on first delivery (outside the tx so it survives a rollback); `approved`→`markPaymentCompleted` (source MP_WEBHOOK); `rejected`/`cancelled`→FAILED in an atomic tx (PaymentEvent + update, P2002 skip) + GA4 `payment_failed`; `refunded`/`charged_back` (only if previously COMPLETED)→REFUNDED + audit + GA4 `refund` (COP value via `mpPurchaseValue`) + compensating CAPI `Refund`.

**Exports:** `WebhookContext`, `InitiateCheckoutInput`, `InitiateCheckoutResult`, `PaymentStatusResult`, `MarkPaymentCompletedInput`, `RecordClientEventInput`, `ReconcileResult`, `MpReconcileResult`, `MpCheckoutData`, `MpProcessInput` (interfaces/types); and functions `initiateCheckout`, `markPaymentCompleted`, `handleOrderPaid`, `handleOrderRefunded`, `handleCheckoutUpdated`, `recordUnhandledPolarEvent`, `recordClientEvent`, `getPaymentStatus`, `reconcileStalePayment`, `findStalePayments`, `reconcileStaleMpPayment`, `findStaleMpPayments`, `initiateMpCheckout`, `processMpPayment`, `handleMpWebhook`.

**Key dependencies:** `crypto`, `prisma` (`../db`), `ServiceError` (`./authService`), `writeAuditEvent` (`../lib/audit`), `sendAdminNotification`/`sendPaymentReceiptEmail` (`../lib/email`), `resolveUserLocale` (`../lib/constants`), `fireAndForget` (`../lib/asyncHelpers`), `sendCapiEvent` (`../lib/metaCapi`), `sendGa4Event` (`../lib/ga4`), pricing helpers (`../lib/pricing`), Polar client (`./polar/client` — `createCheckout`, `getCheckoutSession`), Mercado Pago client (`./mercadopago/client` — `processPaymentDirect`, `getPayment`, `getMpPublicKey`, `createPreference`, `searchPaymentByExternalReference`), `Prisma` types, payment-event constants (`../lib/paymentEvents`), `releaseAccountReceivable` (`./sales/accountReceivableService`).

**Flags:**
- In `reconcileStalePayment`, the Polar `failed` branch writes `eventType: RECONCILER_EVENT_TYPE.EXPIRED` (not a `FAILED` event type) even though it sets `status: "FAILED"` and returns outcome `FAILED_FROM_GATEWAY`. Looks like a copy-paste slip from the `expired` branch — the audit `eventType` mislabels a failure as an expiry. Confidence: medium.
- The `polarCheckoutId` column is overloaded: it stores Polar UUID checkout ids for Polar rows AND a non-UUID `P4A-...` reference for MP rows. This is intentional (documented F-8 rename pending) but is a known smell that forces `findStalePayments` to filter `mpPreferenceId IS NULL` to avoid the Polar SDK crashing on `uuid_parsing`. Confidence: low (documented, not dead code).
- `getOrder` is imported indirectly nowhere here; `getCheckoutSession` is imported twice (top-level alias `createCheckout`/`getCheckoutSession` re-import via dynamic `import("./polar/client")` inside `initiateCheckout` plus a static import at line ~1358). Minor duplication, not dead. Confidence: low.

### backend/src/services/pickService.ts

**Purpose:** Pure business-logic layer for pick (prediction) flows — listing pool matches with lock state, upserting a user's pick, reading match picks (with deadline-gated visibility), and listing a user's own picks. No Express coupling; receives plain data, returns plain data, throws `ServiceError`.

**What it does:**
- **Helpers:** `computeDeadlineUtc(kickoffUtcIso, minutesBefore)` returns the deadline `Date` (kickoff minus N minutes) or null on invalid date. `requireActivePoolMember(userId, poolId)` returns true only for ACTIVE members (write gate). `requirePoolMemberReadAccess(userId, poolId)` returns true for ACTIVE or LEFT members (read gate — LEFT members keep read-only access to preserve points/history per CLAUDE §6 invariant 4).
- **Types:** `PickData`, `GetPoolMatchesInput`/`Result`, `EnrichedMatch`, `UpsertPickInput`/`Result`, `GetMatchPicksInput`/`Result`, `MatchPickEntry`, `GetMyPicksInput`/`Result`.
- **`getPoolMatches`:** Requires read access; loads the pool + `tournamentInstance`; reads `pool.fixtureSnapshot ?? tournamentInstance.dataJson` (pool independence, §6 invariant 6); extracts matches via `extractMatches`; for each match computes `deadlineUtc` and an `isLocked` flag combining host-locked phases (`pool.lockedPhases`) and deadline-passed (`now >= deadline`); returns pool meta + `nowUtc` + enriched matches.
- **`upsertPick`:** Requires ACTIVE membership; loads pool; validates `canMakePicks(pool.status)` (DRAFT→POOL_DRAFT, else CONFLICT); rejects ARCHIVED instances; resolves the match from the snapshot (NOT_FOUND otherwise); blocks placeholder/undetermined teams via `PLACEHOLDER_TEAM_PREFIXES` (MATCH_PENDING); enforces host phase locks (PHASE_LOCKED); validates the deadline with strict `>=` (DEADLINE_PASSED); upserts the `prediction` on the `poolId_userId_matchId` unique key; fire-and-forget `PREDICTION_UPSERTED` audit with ip/userAgent.
- **`getMatchPicks`:** Requires read access; resolves match + deadline; if the deadline has NOT passed returns only the current user's pick (with a message); once passed, returns all ACTIVE members' picks (joining predictions by userId, null where absent), sorted current-user-first then by displayName.
- **`getMyPicks`:** Requires read access; returns all of the user's predictions for the pool ordered by `updatedAtUtc` desc.

**Exports:** functions `computeDeadlineUtc`, `requireActivePoolMember`, `requirePoolMemberReadAccess`, `getPoolMatches`, `upsertPick`, `getMatchPicks`, `getMyPicks`; types `PickData`, `GetPoolMatchesInput`, `EnrichedMatch`, `GetPoolMatchesResult`, `UpsertPickInput`, `UpsertPickResult`, `GetMatchPicksInput`, `MatchPickEntry`, `GetMatchPicksResult`, `GetMyPicksInput`, `GetMyPicksResult`.

**Key dependencies:** `prisma` (`../db`), `writeAuditEvent` (`../lib/audit`), `canMakePicks` (`./poolStateMachine`), `extractMatches` (`../lib/fixture`), `PLACEHOLDER_TEAM_PREFIXES` (`../lib/constants`), `fireAndForget` (`../lib/asyncHelpers`), `ServiceError`/`AuditContext` (`./authService`).

**Flags:** none. (`getMatchPicks` uses `>` for the unlock check while `getPoolMatches`/`upsertPick` use `>=` for lock; this is a deliberate documented choice — picks lock at the deadline millisecond, visibility opens just after — not a bug, but worth noting as a subtle asymmetry.)

### backend/src/services/polar/client.ts

**Purpose:** Thin API-communication wrapper around the `@polar-sh/sdk` for creating checkout sessions and querying orders/checkouts. Contains no business logic — that lives in `paymentService.ts`.

**What it does:**
- **Configuration:** `POLAR_API_KEY()` / `POLAR_PRODUCT_ID()` read env vars lazily. A module-level memoized `_client` is created on first `getClient()` call (throws if `POLAR_API_KEY` is unset). `isPolarConfigured()` returns true only when both key and product id are present.
- **Types:** `CreateCheckoutParams` (amountCents in USD cents, customerEmail, successUrl, cancelUrl, optional locale, and `metadata` carrying poolId/userId/fromCapacity/toCapacity/poolType) and `CheckoutResult` (checkoutId + checkoutUrl).
- **`createCheckout(params)`:** Builds an ad-hoc fixed-price checkout via `client.checkouts.create` (product id, fixed USD price, customer email, successUrl, and `returnUrl: params.cancelUrl` — the SDK's name for the back/cancel URL; without it the cancel-tracking signal is lost, F-2), passing metadata cast to a string record and optional locale. Logs the request/response; throws if no URL is returned; returns `{ checkoutId, checkoutUrl }`.
- **`getCheckoutSession(checkoutId)`:** `client.checkouts.get` for status polling/reconciliation.
- **`getOrder(orderId)`:** `client.orders.get` for post-webhook verification.

**Exports:** `isPolarConfigured`, `createCheckout`, `getCheckoutSession`, `getOrder`; types `CreateCheckoutParams`, `CheckoutResult`.

**Flags:** `getOrder` has no apparent consumer in this batch (paymentService uses `getCheckoutSession` for reconciliation, not `getOrder`). Possible dead export — verify across the repo before removing. Confidence: low.
